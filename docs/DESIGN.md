# shiftflow Supabase 版 設計書(第2版)

状態: **実装済み**(2026-09-29 第2版。実環境での動作確認はこれから。実装で変えた点は末尾の「実装で決めたこと」)

個人用の勤務登録アプリを、身内の数人〜数十人で使える Supabase 版として作った。
第1版(Google ログイン方式)は設定の手間が大きかったため、ログインを「社員番号+PIN」に変えて全体を簡単にした。
第1版の内容は git の履歴(このファイルの過去の版)で見られる。

## 0. 仕様の要点(以前のアプリから引き継いだもの。第1版から変更なし)

| 項目 | 現行の挙動 |
|---|---|
| マスタ | 番号 / 種別(泊・日勤・休日) / 平日出勤 / 平日退勤 / 休日出勤 / 休日退勤 / 泊(泊地)。時刻は `(9:01)` や `09:01:00` を `9:01` に正規化(2026-10-04 に、泊用の任意の列 平休出勤 / 平休退勤 / 休平出勤 / 休平退勤 を追加。「実装で決めたこと」参照) |
| 平/休 | 土日・祝日・12/30〜1/3 は休、他は平。表示のみ |
| 予定 | すべて終日。泊=番号/出勤時間(2行目に泊地)、日勤=番号/出勤〜退勤、非番=「〜」/退勤時間、休日=番号/メモなし(休日用カレンダー)、手入力=入力文字/メモなし |
| 非番 | 前日が泊なら自動で非番。月末が泊なら翌月1日の非番も作る(泊の出勤・非番の退勤は、泊の日と翌日の平休で列を選ぶ。2026-10-04 から) |
| 手修正メモ | 手で書き換えた日はその内容をメモの1行目にする(泊地は2行目に残る)。番号を選び直すと自動値に戻る |
| 登録 | 保存 → その月(+翌月1日の非番)のアプリ作成予定だけ削除 → 作り直し。印は `extendedProperties.private.shiftflow` = `day` / `offduty` |
| リセット | 月を選んで、アプリ作成予定だけ削除し、その月の記録も消す |
| 画面 | 月切替(当月より前に戻れない)、1日1行、今日の行へスクロール、番号のボタン一覧+手入力+クリア |

→ 実装済みのもの(`supabase/functions/_shared/plan.js` とそのテスト、カレンダー操作)はそのまま使う。

## 1. 決まったこと(第2版)

| 項目 | 決定 |

| ログイン | **社員番号(7桁)+ PIN(4桁の数字)**。登録が無ければ弾く。Google ログインは使わない |

| デプロイ | **GitHub Actions で自動**(main に push すると DB・Edge Functions・画面が反映される)。ターミナル不要 |
| 停止対策 | **cron-job.org から Supabase を直接**6時間ごとに呼ぶ(GitHub を経由しない) |
| 課金 | 今は作らない。`profiles.plan` 列だけ用意しておく(6章) |

## 2. 画面

```
index.html(最初の画面)
 ├ [利用者] タブ: 社員番号 + PIN → ログイン
 │     └ 「新規登録」→ register.html
 │           社員番号 / 名字 / 名前 / PIN(2回)/ 共通パスワード → 登録 → 自動でログイン
 └ [管理] タブ: 管理用パスワード → admin.html

settings.html  区所を選ぶ / 勤務用・休日用カレンダーID / 保存すると自動で接続テスト
input.html     勤務入力(第1版の画面をそのまま使う)→ 登録 / リセット
admin.html     ダッシュボード(タブで切り替え)
help.html      使い方(未ログインでも読める)
```

ログイン後の流れ: 初回は `settings.html` → 区所とカレンダーIDを保存(接続テストが通る)→ `input.html`。2回目以降は `input.html` に直行。

### 管理画面(ダッシュボード)

| タブ | 内容 |
|---|---|
| 概要 | 数字のカード(登録人数・接続テスト済み・30日以内に登録した人・区所数)、区所ごとの人数、最近の登録 |
| 利用者 | 一覧(社員番号・氏名・区所・接続テスト・最終ログイン・最終登録)。**削除**、**PINの再設定**(PIN を忘れた人向けに仮のPINを発行) |
| マスタ表 | 区所を選ぶと、そのマスタを全列(番号・種別・平日出勤・平日退勤・休日出勤・休日退勤・泊・平休出勤・平休退勤・休平出勤・休平退勤)の表で表示。CSV で書き出し |
| マスタ登録 | 区所の追加・名前変更・削除。区所を選んで CSV を選ぶ → 取り込む内容を表で確認(問題の行は赤で取り込み不可)→ 入れ替え |
| 設定 | 共通パスワードの変更、登録用アドレス(サービスアカウント)の表示 |

見た目は、カード型の数字とタブ切り替えのダッシュボードにする(PC でもスマホでも見られる)。

## 3. しくみ

### 3-1. ログイン(Supabase Auth のメール+パスワードを内部で使う)

- 利用者から見えるのは社員番号と PIN だけ。内部では Supabase Auth のユーザーとして
  - メール: `<社員番号>@users.shiftflow.invalid`(実在しない専用のアドレス。メールは送らない)
  - パスワード: PIN から作る値
  で登録・ログインする。これで Supabase の RLS(`auth.uid()`)や、ログイン試行回数の制限をそのまま使える
- PIN は **4桁**(6桁から変更。1万通りだが、社員番号ごとに5回失敗で15分ロックするため総当たりは現実的でない。内部パスワードは `sf-` を付けて7文字)
- Supabase Auth の「新規ユーザーの登録を許可」は**オフ**にし、ユーザーは Edge Function `sign-up` だけが作る(共通パスワードを確かめてから作るため)
- 管理者も Supabase Auth のユーザー(`admin@admin.shiftflow.invalid` + 管理用パスワード)。`profiles.role = 'admin'` で区別する
- 管理用パスワードは長め(12文字以上を推奨)。ログイン試行の制限は Supabase Auth のものを使う

### 3-2. 新規登録(Edge Function `sign-up`)

1. 共通パスワードを確かめる(DB にはハッシュだけ保存。間違いが続いたら一定時間受け付けない)
2. 社員番号が7桁の数字か、まだ登録されていないかを確かめる
3. Supabase Auth のユーザーを作り、`profiles` に社員番号・名字・名前を入れる
4. 画面はそのまま社員番号+PIN でログインする

### 3-3. カレンダー登録(第1版から変更なし)

- 利用者は勤務用・休日用のカレンダーを、サービスアカウントのメールアドレスと「すべての予定の詳細の変更や表示ができます」の権限で共有する(**この1回の共有はどうしても必要**。アプリが利用者のカレンダーに書く方法として、これが一番設定が少ないため)
- Edge Function はリクエストに書かれたカレンダーIDを使わず、`user_settings` に登録済みのIDだけを使う
- 同じカレンダーIDは1人しか使えない。メールアドレス形式のID(メインのカレンダー)は使わせない(社員番号ログインではメールアドレスが分からず、本人のものか確かめられないため)。**このアプリ用に新しく作ったカレンダーを使う**ようヘルプで案内する
- 祝日は Google の公開祝日カレンダーをサービスアカウントで読んで DB にキャッシュ

### 3-4. データベースの停止対策

- 無料プランは、過去1週間のデータベースへのアクセスがほとんどないと一時停止する(Supabase 公式: 「1日に数回のアクセスが1週間続けば十分」。停止の約1週間前に警告メールが届く。停止後1年以内ならダッシュボードから復元できる)
- `keepalive()` という関数(DB を1回読んで時刻を返すだけ。個人のデータは返さない)を用意し、未ログインでも呼べるようにする
- cron-job.org から6時間ごとに `POST https://<ref>.supabase.co/rest/v1/rpc/keepalive` を呼ぶ(ヘッダーに公開用キー)。トークンや GitHub は使わない

### 3-5. デプロイ(GitHub Actions)

| ワークフロー | いつ | すること |
|---|---|---|
| `deploy-supabase.yml` | `supabase/` を変えて main に push したとき(手動でも可) | `supabase link` → `supabase db push`(SQL の反映)→ `supabase functions deploy` |
| `pages.yml` | `web/` を変えて main に push したとき | `web/` を GitHub Pages に公開 |
| `test.yml` | コードを変えたとき | 予定の組み立て・カレンダー操作のテスト |

GitHub の Secrets に入れるもの(最初に本人が1回だけ): `SUPABASE_ACCESS_TOKEN`、`SUPABASE_PROJECT_ID`、`SUPABASE_DB_PASSWORD`。
サービスアカウントの鍵は Supabase のダッシュボードの Edge Functions → Secrets に本人が入れる(GitHub には置かない)。

## 6. 課金を足すとき(今は作らない)

- **方針(2026-09-29)**: `profiles.plan` の枠だけ最初から用意する。来春は無料で集客し、うまくいかなければそのまま無料で続ける。有料にすると決めた時点で、下の内容を足す

- `profiles.plan`(今は常に `free`)で、使える機能を分けられるようにしておく
- 身内だけなら、アプリの外(現金・送金アプリなど)で受け取り、管理画面で `plan` を切り替えるのが一番簡単
- アプリの中で払えるようにする場合は Stripe などの決済サービスを使う(Google は不要)。そのときは
  - 決済サービスのアカウント(本人確認・振込先口座)
  - 支払い完了を受け取る Edge Function(`plan` を書き換える)
  - 特定商取引法に基づく表記のページ
  - Supabase の有料プランへの切り替えの検討(無料プランは一時停止があるため)
  が必要になる

### 6-1. 有効期限の設計(案・まだ作らない)

年500円(任意または必須は未定)で集金し、払った人の有効期限を管理するための設計。**この節は設計だけで、SQL もコードもまだ書かない。**

**列の追加(新しい migration ファイルで行う。`init.sql` は書き換えない)**

| 列 | 型 | 既定値 | 意味 |
|---|---|---|---|
| `profiles.paid_until` | `date`(null 可) | 導入時に全員へ入れる(下記) | この日まで登録できる。null は期限なし(管理者・無料のまま使う人) |

- `plan` は残す。`free` = 無料のまま、`paid` = 有料。`plan = 'paid'` の人だけ `paid_until` を見る(`free` は期限を見ない)
- 既存の行は壊れない(列を足すだけ)。カレンダーの予定は Google 側にあるので影響しない

**判定ルール(1か所にまとめる)**

- 「登録できる」 = `plan = 'free'` または `paid_until is null` または `paid_until >= 今日(日本時間)`
- 期限切れで止めるのは **`register-month` だけ**(新しい登録・登録し直し)。ログイン・閲覧・設定・PIN の変更・`delete-month`(予定の削除)は止めない
- 判定は Edge Function 側で行い、`requireMember` が読む `profiles` の列に `plan, paid_until` を足して、`ctx` に `canRegister` を持たせる。画面側の判定は表示のためだけで、止めるのはサーバー側
- 止めたときは `403` と `code: "expired"` を返し、画面は「有効期限が切れています。管理者に連絡してください」と出す
- 利用者は `profiles` を読めるので、自分の `plan` と `paid_until` は画面に出せる(設定画面に「有効期限: ○年○月○日」)。書き込みは Edge Function だけ(現状どおり)

**管理画面**

- 利用者一覧(`admin_stats()` の `users_list`)に `paid_until` を足す。期限が近い(30日以内)人・切れた人は目立たせる
- `admin-users` に `action: "set-paid"`(`paid_until` を指定、または「今日から1年」)と `action: "set-free"` を足す。入金を確かめたあと、管理者が押す

**導入の順番(誤って全員を期限切れにしないため)**

1. migration で `paid_until` を足す。**同じ migration で既存の全員に猶予の日付(例: 半年先)を入れ、`plan` を `paid` にする**(判定コードはまだ出さない)
2. 管理画面の表示と、`admin-users` の `set-paid` を出す
3. 周知(料金・開始日・払い方・払わなかったときの扱い)
4. 判定コード(`register-month` の停止)を出す。この時点で、猶予の日付までは何も起きない
5. 猶予の日付が近づいたら、管理画面で払った人の `paid_until` を更新する

**集金(決めること)**

- 払い方: 現金・送金アプリで受け取り、管理画面で更新する(最小)。Stripe は人数が増えてから
- 年の途中で使うのをやめた人への返金は、しない(規約・使い方に書く)
- 会社の資料を使っていないこと、時刻は利用者が自分で確認すること、を使い方ページに一言書く
- 有料にする(必須にする)前に、特定商取引法に基づく表記の要否を確認する

**テスト(作るときに足すもの)**

- 判定関数の単体テスト: `free` は常に可、`paid` で期限が今日・昨日・明日・null のとき、日本時間での日付の境目
- 既存の全員に `paid_until` を入れる migration のあと、期限切れの人が0人であること(SQL で確かめる)

## 7. 最初に本人がやること(実装後)

1. Supabase のプロジェクトを作る(Tokyo)。Authentication で「新規ユーザーの登録を許可」をオフ、「メールの確認」をオフ

7. 管理画面で区所を作り、区所ごとにマスタの CSV を取り込む

## 実装で決めたこと(設計からの変更・具体化)

- **ログインは Edge Function 経由**: 画面から Supabase Auth に直接ログインさせず、`login`(社員番号+PIN)と `admin-login`(管理用パスワード)が検証してセッションを返す。社員番号ごとの失敗回数を数えて5回で15分ロックするため(Supabase Auth だけでは、社員番号ごとのロックができない)。新規登録の共通パスワードも、IPごとに5回でロック
- **管理用パスワードはシークレット `ADMIN_PASSWORD`(12文字以上)**: DB に置かず、Supabase の Edge Functions → Secrets に置く(SQL を実行する手順を減らすため)。ログインのたびに管理用ユーザーのパスワードを使い捨ての値に変える
- **共通パスワードは管理画面から設定**(DB にハッシュだけ保存)。設定するまで新規登録は受け付けない
- **PIN の変更は `change-pin` 関数**: PIN から Supabase Auth のパスワードを作る変換(`sf-` + PIN)を、画面に持たせないため
- 管理画面のダッシュボード用の数字は SQL 関数 `admin_stats()` でまとめて返す。勤務の中身(番号・メモ)やカレンダーIDは管理者にも見えない(RLS)
- 全角の数字で入力しても、半角にして受け付ける(スマホの日本語キーボード対策)
- 勤務入力の手入力欄に一覧の番号を全角で入れても(「１０１」「Ｅ」)、一覧の番号として扱う(入れ終えたときに一覧の番号に直す)。一覧にない番号は打ったまま保存する
- DB の停止対策は `keepalive()`(未ログインで呼べる関数)を cron-job.org から POST で呼ぶ。URL とキーは管理画面の設定タブに表示する
- 自動デプロイは `deploy-supabase.yml`(`supabase db push` と `supabase functions deploy`)。Secrets が未登録のあいだは、何もせずに終わる(失敗にしない)
- 内部用のメールは `<社員番号>@users.shiftflow.invalid`、管理用は `admin@admin.shiftflow.invalid`
- **出勤を2件で登録する設定**(`user_settings.split_day_events`。利用者が設定画面で選ぶ): 勤務用の出勤(日勤・泊)の終日の予定に続けて、メモの1行目の時間で時間つきの予定(日本時間)を作る。日勤は出勤〜退勤、泊は出勤から1時間。退勤が出勤より前の時刻(22:00〜6:00 など日をまたぐもの)も1時間(翌日まで伸ばすと翌日の予定の並びが変わるため。時間を確かめられれば十分)。手で書き換えたメモの全角の数字や「～」も時間として読む。マスタにない手入力の番号も日勤と同じに分ける(ただし記号だけのもの(「〜」「-」「→」など)・「非」「明」だけのもの・「非番」「明け」「明番」を含むもの・「休」を含むもの(公休・年休など)は非番・休みなので1件のまま。「明石」のような駅名は勤務として分ける。「休出」「休日出勤」のように「出」「勤」も含むものは出勤なので分ける)。時間の区切りは「-」「ー」「―」「−」「～」などの横棒・「→」「から」のどれでも可。時間でないメモ・出勤が24時以降のときは1件のまま(24時以降は翌日の予定になり、月末だと翌月1日に入って、登録し直しで消えずに増えるため)。削除は印で探すので、時間つきの予定も消える
- **平休・休平の出勤・退勤**(`shift_master.weekday_holiday_start` / `weekday_holiday_end` / `holiday_weekday_start` / `holiday_weekday_end`。どれも任意。泊の番号だけで使う): 泊の出勤と、翌日の非番の退勤は、泊の日と翌日の平休で列を選ぶ。
  - 平→平: 平日出勤・平日退勤 / 休→休: 休日出勤・休日退勤
  - 平→休: 平休出勤(空なら平日出勤)・平休退勤(空なら休日退勤)
  - 休→平: 休平出勤(空なら休日出勤)・休平退勤(空なら平日退勤)
  - 休日の列が空なら平日の列。平休の判定は今までどおり(土日祝・12/30〜1/3が休)。日勤は今までどおり、その日の列だけ
  - 1日が非番のときは前月末、翌月1日が泊のときは翌月2日の平休を見るので、登録では祝日を前月末〜翌月2日で読む
  - CSV の4列は無くてもよく、無いマスタは今までと同じ動き
- **マスタの番号は半角にそろえて取り込む**(2026-10-05): CSV の番号の全角の英数字・記号と全角の空白は、取り込む前の確認の段階で半角にする(日本語の文字はそのまま)。全角と半角で同じになる番号は「番号が重複」。すでに入っているマスタは、取り込み直すまで変わらない
