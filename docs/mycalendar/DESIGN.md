# 自作カレンダー(アプリ内カレンダー)の設計メモ(2026-11-02・まだ作っていない)

## 目的
- 点呼の確認など、自分の勤務を見やすく見るために、アプリ内にカレンダー画面を持つ
- 家族などと共有したい人は、これまでどおり Google カレンダーにも同期できる(チェックで選ぶ)
- Google カレンダーを使わない人も、保存だけで使える

## 決めたこと(相談の結果)
| 項目 | 内容 |
|---|---|
| 位置づけ | 自作カレンダー=自分用(点呼など)。Google カレンダー=家族などへの共有用。両方に入れることも、自作だけにすることもできる |
| 表記 | 設定どおり(`1(10:00)` のような時間つき、出勤2件、泊、休日など)。予定の組み立ては `shift-calendar.ts` の同じものを使い、両方で表記がそろうようにする |
| 保存の流れ | 入力 → `shift_records` に保存(必ず) → 「Google カレンダーにも登録する」にチェックがあるときだけ Google に登録。チェックの状態は設定に覚える |
| Google だけ失敗したとき | 自作側は保存済み。「Google への登録に失敗、保存はできています」と出して、もう一度「登録」で直す |
| ホーム画面 | `calendar.html` を別アプリとして追加できるようにする(専用の manifest・アイコン)。ログインは同じ社員番号とパスワード。iPhone は追加したアプリで最初に1回ログインが必要(Safari とは共有されない) |
| 保存期間 | 勤務記録は前後1年に延ばす(今は前月の1日より前を毎日削除)。1人 約110KB(1行 約150バイト × 730日)で、1,000人でも約110MB。無料枠500MBに収まる。削除の基準を「13か月前より前」に変える |
| 写真 | 予定に写真を付ける。画面で縮小(長い辺1280px・JPEG 画質70%・約150KB)、位置情報は canvas で描き直して消す(お問い合わせの画像と同じ方法)。予定1件につき3枚まで。Supabase Storage(無料枠1GB)に置く。**前月の1日より前の写真は毎日の自動削除で Storage からも消す**。Google の予定には付かない(画面に書く) |

## いま Google に登録している人はどうなるか
| 項目 | 内容 |
|---|---|
| 初期値 | (2026-11-03 変更: これから使い始める人は、チェックなし。migration `20261103000003`。今 Google に登録している人はチェックを入れたまま)カレンダーIDを設定済みの人は、チェックを最初から入れた状態にする。「登録」の動きは今までと同じ(Google に登録される)。自分で外した人だけ保存のみになる |
| 新しく使い始める人 | カレンダーIDが空なら、チェックは外した状態から始まる。保存のみで使える |
| 変わらないもの | 設定画面のカレンダーID・接続テスト・簡単設定。すでに Google に入っている予定。リセットと登録し直し |
| 実装 | 設定の保存先に「Google にも登録する」の列を足す。既存の利用者の初期値は、カレンダーIDがあるかどうかで migration が入れる |
| 古い画面への備え | 画面を更新していない人からのリクエストにはこの値が付かない。サーバーは、値がないときは「登録する」として扱う(更新のタイミングで登録が止まらないようにする) |

## 接続テストとボタンの扱い
- 「保存して接続テスト」ボタンは、Google に登録する人には今のまま必要(カレンダーIDを保存し、書き込めるか確かめる)
- 「Google にも登録する」を外した人(保存だけで使う人)は、接続テストなしで使える。接続テスト済みを条件にするのは、チェックを入れたときだけ
- 保存だけの人にも設定を保存するボタンが必要なので、ボタンの名前と動きは、チェックの有無で「保存」「保存して接続テスト」に変える(作るときに決める)
- 「Google にも登録する」を外しているあいだは、カレンダーID(勤務用・休日用・非番の時間用)が入っていても、接続テストなしで保存できる。IDは消さずに残し、あとでチェックを入れ直したときにそのまま使う。接続テストが必要なのは、このチェックを入れたときだけ(今の画面の「非番の時間用IDを入れているあいだは、非番のチェックを外していても接続テストをする」は、Google のチェックが入っているときの話として残す)

## 保存期間を1年にするとき、マスタ(古い切替日)の削除も合わせる
- **今のマスタの消える条件**(`purge_old_master_periods`・毎日の削除と一緒に動く): ある切替日のマスタ(古い方)は、**その次の切替日が「前月の1日」以前に始まっていて、次の切替日にマスタの行が入っているとき**に、行ごと消える。つまり「切り替わり後」ではなく、「切り替わってから、次の切替日が前月の1日より前になった(約1〜2か月たった)あと」。次の切替日のマスタが空なら消さない(CSV の入れ忘れで、中身のあるマスタが消えないように)
- **問題**: 勤務の記録を過去1年見られるようにしても、切替から約2か月たつと古いマスタが消える。すると、1年前の月をカレンダーで開いたとき、時間・泊地が出ない(番号だけ・手入力扱い)か、新しいマスタの時間で出てしまう
- **直し方**: 古い切替日を消す基準を、勤務の記録の保存期間(13か月前)に合わせる。「次の切替日が13か月前以前」になってから消す。この変更は、記録の保存期間を延ばす migration と**同じ migration**で出す(別々にすると、記録だけ残ってマスタが先に消える期間ができる)
- **今すでに消えている古いマスタは戻らない**(今の基準は約2か月)。ただし、運用は10月のダイヤ修正のあとからなので、実際に困るのは「10月より前の月を開いたとき」だけ(運用前なので、勤務の記録もない)。カレンダーの説明にも、「見返せるのは運用を始めた月から」と書く(設定の一番上の説明)
- 管理画面の「CSVで保存」の説明にある「古い切替日は自動で消える」の文面も、1年に合わせて直す(README・`docs/DESIGN.md` の「マスタの切替」も)
- 自動テストに足す: 次の切替日が13か月前より新しいあいだは古いマスタが残る・13か月前より古く、次にマスタの行があれば消える・次が空なら消えない

### 半年ごとのダイヤ改正・修正でも1年見られるか
- 見られる。消す条件は「古いマスタの期間が、保存期間(13か月)にまったくかからなくなったとき」(次の切替日が13か月前以前になったとき)。1年前の日付を含むマスタは残る
- 半年ごとに切り替わる場合、1つの区所が持つのは最大3つ程度(今のマスタ・半年前・1年前)。次の切替から13か月たつと、一番古いものが消える。容量は気にしなくてよい
- 今の基準(前月の1日)のままだと、切替から約2か月で前のマスタが消える。そのため基準を13か月に変える(上の「直し方」)
- 次の切替日のマスタ(CSV)が空なら、前のマスタは消さない(今の安全装置のまま)
- **運用の前提(2026-11-02)**: 運用は先月(10月)から。10月に「ダイヤ修正」の切替があった直後で、その前のマスタの記録は今の運用に関係しない。**保存期間を延ばす migration を出せば、10月以降の記録とマスタは、消えずに1年分たまっていく**。すでに消えた古いマスタ(10月より前)は戻さなくてよい。次の切替(半年後)の前のマスタも、13か月は残る
- 念のため、管理画面の「CSVで保存」で、今のマスタを書き出しておく

### マスタは個数の上限を付けず、期間だけで消す(決定 2026-11-02)
- 古いマスタ(切替日)を消すのは、**期間だけ**で決める。「3つまで」のような個数の上限は付けない(上限を付けると、1年前の月が見られなくなるおそれがあるため)
- 消す条件: その次の切替日が「13か月前の月初」以前になったとき(かつ、次の切替日のマスタに行が入っているとき)。「1年」ではなく**13か月**(月またぎの非番判定が前月末の記録を使うための1か月の余裕。記録の削除の基準と同じ)
- 半年ごとの切替なら、結果として3つ前後が残る。ダイヤ修正が年に何度かあれば、それより多く残る(それでよい)
- 管理画面では、残っているマスタが切替日ごとのタブに並ぶ。手で消すこともできる(今のまま)
- 自動テスト: 個数が多くても、13か月以内に使われるマスタは消えない

## 気をつける点
- 自作だけで保存した月を、あとで Google にも登録するときは、今の「登録し直し」と同じ処理でまとめて入れる(重複しない)
- Google 側の予定を手で消したり直したりしても、自作側には反映されない。アプリで入れ直したときに両方そろう
- 写真を毎日全員が撮ると 1GB に近づく。使用量を管理画面で見られるようにする
- オフライン表示(Service Worker)は必須ではない。あとで足す

### 2-1. 設定の一番上: shiftflowカレンダーの使い方・仕様
折りたたまずに、最初に見える説明のカードにする。書く内容(作るときに文面を決める)。
- できること: 勤務(勤務入力で保存したもの)と、自分の予定を、月表示で見る。スタンプ・TODO・重要メモ・画像を置ける
- 勤務の予定は、勤務入力で直す(カレンダーからは直せない)。勤務の表記は、勤務入力の設定どおり
- ラベルのチップの使い方(押すと消える・戻る。色と順番は設定で決める)
- 保存のルール: 見返せるのは過去1年まで。予定の写真は予定の終了日から1か月で消える(1つの予定に3枚まで)。画像の置き場は1人10枚まで。繰り返しの予定の元の1件は終わるまで残る
- Google との関係: 勤務は「Googleにも登録する」のチェックで同期できる。カレンダー自体は **1アカウント1人**。家族に見せたいときは、(1)このアプリのURLを教えて、その人が自分のアカウントでログインして使う (2)Googleカレンダーへの同期に任せる、のどちらか

- 画面の色合いとパソコンの表示は、設定の一番下にある、という案内

## 3. 画像と保存期間(容量を守る)
| 項目 | 移植元 | ここでの決定 |
|---|---|---|
| 「画像」(ヘッダーの置き場。子供の日程表など) | 300枚・長辺1800px・約780KB | **1人10枚まで**。長辺1400px・約400KB以下に縮小(1人 約4MBまで)。自動では消えない(自分で消す) |
| 予定に付ける写真 | 枚数の制限は広い・長辺1280px・約500KB | **1つの予定に3枚まで**。長辺1280px・約150〜200KB以下に縮小(位置情報は消す) |

## 5段階目で決めたこと・変えたこと(2026-11-02)
- **写真のファイルを消す仕組み**: 設計では「毎日3時の自動削除で Storage から消す」としていたが、DBの毎日の削除(pg_cron)からは Storage のファイルを消せない(Storage の API で消す必要がある)。cron-job.org などの外部の仕組みを増やさないため、**持ち主がカレンダーを開いたときに、期限(予定の終了日から1か月)を過ぎた自分の写真を、ファイルを消してから行を消す**形にした。ファイルを消せなかったときは、行を残して次に開いたときにやり直す(ファイルの消し忘れが出ない)。長く開かない人の期限切れの写真は、その人が開くまで残る(1人あたりの量は小さい)。あとで外部から毎日消したくなったら、service_role の Edge Function を足せる(`cal_photos.expires_on` が期限)
- 予定を消すときは、写真のファイルを先に消す(予定を消すと写真の行も消え、ファイルだけ残るため)。消せなかったら予定も消さずに知らせる
- 古い予定を消す毎日の処理は、写真が残っている予定は消さない(写真が先に消えた翌日に、予定が消える)。そのため、ファイルの消し忘れが出ない
- 予定の写真: 長い辺1280px・約200KB以下のJPEG・1つの予定に3枚・繰り返しの予定の写真は自動では消えない
- 保存期間(migration `20261102000002_retention`): 勤務の記録と古いマスタは13か月、カレンダーの予定・スタンプは12か月(画面も12か月前の月まで)
- 管理者が利用者を消したときの Storage のファイルは、7段階目で片付くようにした(`admin-users` が、利用者を消す前に `<user_id>/` の下を全部消す。消せなければ利用者も消さない)

## ホーム画面のアイコン(2026-11-04 追記)
- **できないこと**: すでにホーム画面にあるアイコンを、あとから自動で入れ替えること(スマホの決まり。「ホーム画面に追加」を押した時点の画像が保存される)。だから「選んでから追加する(すでにある人は消して追加し直す)」形にした
- **仕組み**: 選んだアイコンを、ページが指す `apple-touch-icon`・タブのアイコン・manifest(選んだアイコン入りのものをその場で blob で作り、`<link rel="manifest">` を差し替える)に反映する。iPhone は apple-touch-icon(180px)、Android(Chrome)は追加の時点の manifest の icons(192・512・maskable 512)が使われる。**Android・iPhone とも、実機で確認済み(2026-11-04。試作の青・緑で)**
- **選べるもの**: コードの中にある「いまの(電車)」だけ(`web/calendar/icons/`。2026-11-04 のご依頼で、試作の青・緑・オレンジは外した)と、管理画面で足したもの(表 `app_icons`・Storage `app-icons`)。管理画面で足したものは、「いまの(電車)」の後ろに並ぶ。試作のときに端末が覚えた青・緑・オレンジは、今のアイコンのまま扱う
- **覚え方**: 選んだものの URL 一式を、この端末の localStorage に JSON で覚える(開いた直後、通信の前に反映できる)。前の版は id だけ(`"green"`)を覚えていたので、それも読める。管理画面で消された・隠されたアイコンを覚えていたら、読み込めたときに覚えを消して今のアイコンに戻す
- **管理画面**(設定タブ): 足す(画像を選ぶと、枠の中でドラッグして位置・スライダーで大きさ・矢印キーで微調整し、アイコンにする範囲を決める。点線の円は、丸く切られても残る範囲の目安(直径80%)。できあがりと丸く切られたときのプレビューが出る。窓は画像の外に出ず、窓の中が192px未満になる大きさにはできない。決めた範囲を、透明は白で塗り、512・192・180px の PNG にする。短い辺が192px未満の画像は使えない)・名前を直す(画像は直せない。入れ替えたいときは消して足し直す)・↑↓で並べ替え・隠す・消す。最大20件(DB でも確かめる)。画像が途中で入らなければ、行も画像も消して追加しない
- **maskable**: 512px の画像をそのまま使う(端が丸く切られることがある。管理画面に「大事な絵は真ん中に」と書いた)
- **本番の確認**: migration `20261104000001` で公開バケット `app-icons` と管理者の権限ができるか(CHECKLIST の末尾。作れなかったときの手で作る SQL もある)
