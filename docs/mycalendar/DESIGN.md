# 自作カレンダー(アプリ内カレンダー)の設計メモ(2026-11-02・まだ作っていない)

## 目的
- 点呼の確認など、自分の勤務を見やすく見るために、アプリ内にカレンダー画面を持つ
- 家族などと共有したい人は、これまでどおり Google カレンダーにも同期できる(チェックで選ぶ)
- Google カレンダーを使わない人も、保存だけで使える

## 決めたこと(相談の結果)
| 項目 | 内容 |
|---|---|
| 位置づけ | 自作カレンダー=自分用(点呼など)。Google カレンダー=家族などへの共有用。両方に入れることも、自作だけにすることもできる |
| 表記 | 設定どおり(`1(10:00)` のような時間つき、出勤2件、泊、休日など)。予定の組み立ては `shift-calendar.ts` の同じものを使い、両方で表記がそろうようにする |
| 保存の流れ | 入力 → `shift_records` に保存(必ず) → 「Google カレンダーにも登録する」にチェックがあるときだけ Google に登録。チェックの状態は設定に覚える |
| Google だけ失敗したとき | 自作側は保存済み。「Google への登録に失敗、保存はできています」と出して、もう一度「登録」で直す |
| ホーム画面 | `calendar.html` を別アプリとして追加できるようにする(専用の manifest・アイコン)。ログインは同じ社員番号とパスワード。iPhone は追加したアプリで最初に1回ログインが必要(Safari とは共有されない) |
| 保存期間 | 勤務記録は前後1年に延ばす(今は前月の1日より前を毎日削除)。1人 約110KB(1行 約150バイト × 730日)で、1,000人でも約110MB。無料枠500MBに収まる。削除の基準を「13か月前より前」に変える |
| 写真 | 予定に写真を付ける。画面で縮小(長い辺1280px・JPEG 画質70%・約150KB)、位置情報は canvas で描き直して消す(お問い合わせの画像と同じ方法)。予定1件につき3枚まで。Supabase Storage(無料枠1GB)に置く。**前月の1日より前の写真は毎日の自動削除で Storage からも消す**。Google の予定には付かない(画面に書く) |

## いま Google に登録している人はどうなるか
| 項目 | 内容 |
|---|---|
| 初期値 | カレンダーIDを設定済みの人は、チェックを最初から入れた状態にする。「登録」の動きは今までと同じ(Google に登録される)。自分で外した人だけ保存のみになる |
| 新しく使い始める人 | カレンダーIDが空なら、チェックは外した状態から始まる。保存のみで使える |
| 変わらないもの | 設定画面のカレンダーID・接続テスト・かんたん設定。すでに Google に入っている予定。リセットと登録し直し |
| 実装 | 設定の保存先に「Google にも登録する」の列を足す。既存の利用者の初期値は、カレンダーIDがあるかどうかで migration が入れる |
| 古い画面への備え | 画面を更新していない人からのリクエストにはこの値が付かない。サーバーは、値がないときは「登録する」として扱う(更新のタイミングで登録が止まらないようにする) |

## 接続テストとボタンの扱い
- 「保存して接続テスト」ボタンは、Google に登録する人には今のまま必要(カレンダーIDを保存し、書き込めるか確かめる)
- 「Google にも登録する」を外した人(保存だけで使う人)は、接続テストなしで使える。接続テスト済みを条件にするのは、チェックを入れたときだけ
- 保存だけの人にも設定を保存するボタンが必要なので、ボタンの名前と動きは、チェックの有無で「保存」「保存して接続テスト」に変える(作るときに決める)
- 「Google にも登録する」を外しているあいだは、カレンダーID(勤務用・休日用・非番の時間用)が入っていても、接続テストなしで保存できる。IDは消さずに残し、あとでチェックを入れ直したときにそのまま使う。接続テストが必要なのは、このチェックを入れたときだけ(今の画面の「非番の時間用IDを入れているあいだは、非番のチェックを外していても接続テストをする」は、Google のチェックが入っているときの話として残す)

## 自動テストに足す項目
| 種類 | 確かめること |

| サーバー(Deno) | チェックなしの登録で Google を呼ばない(保存だけで終わる) |

| サーバー(Deno) | チェックの値がない古い画面からのリクエストは「登録する」として扱う |
| サーバー(Deno) | Google だけ失敗しても、保存は残る(保存済みのメッセージが返る) |
| サーバー(Deno) | 自作だけで保存した月を、あとで Google に登録し直しても、予定が重複しない |
| DB(migration・権限) | 既存の利用者の初期値(カレンダーIDがあればチェックあり、空ならなし)が入る |
| DB(migration・権限) | 保存期間を前後1年に変えても、それより前の記録だけが消える。他人の記録は見えない |
| 画面(E2E) | チェックを外したまま、IDが入っていても、接続テストなしで保存できる。チェックを入れ直すと、接続テストが必要になる |
| 画面(E2E) | チェックを外して登録すると、接続テスト前でも保存できて、Google には何も送られない |

| 画面(E2E) | カレンダー画面を別アプリとして開いたとき、ログインが必要で、一度入れば次から開ける |
| 画面(E2E) | 写真を付けると縮小される(長い辺1280px以下・位置情報なし)。4枚目は付けられない |
| DB・Storage | 前月の1日より前の写真が、自動削除で Storage からも消える |

## 気をつける点
- 自作だけで保存した月を、あとで Google にも登録するときは、今の「登録し直し」と同じ処理でまとめて入れる(重複しない)
- Google 側の予定を手で消したり直したりしても、自作側には反映されない。アプリで入れ直したときに両方そろう
- 写真を毎日全員が撮ると 1GB に近づく。使用量を管理画面で見られるようにする
- オフライン表示(Service Worker)は必須ではない。あとで足す

3. 写真の添付(縮小・Storage・3枚まで)と、前月より前の自動削除
4. 使用量の表示(任意)

## 1. 作り方(移植)

### 2-1. 設定の一番上: shiftflowカレンダーの使い方・仕様
折りたたまずに、最初に見える説明のカードにする。書く内容(作るときに文面を決める)。
- できること: 勤務(勤務入力で保存したもの)と、自分の予定を、月表示で見る。スタンプ・TODO・重要メモ・画像を置ける
- 勤務の予定は、勤務入力で直す(カレンダーからは直せない)。勤務の表記は、勤務入力の設定どおり

- 保存のルール: 見返せるのは過去1年まで。予定の写真は予定の終了日から1か月で消える(1つの予定に3枚まで)。画像の置き場は1人10枚まで。繰り返しの予定の元の1件は終わるまで残る

## 3. 画像と保存期間(容量を守る)
| 項目 | 移植元 | ここでの決定 |
|---|---|---|
| 「画像」(ヘッダーの置き場。子供の日程表など) | 300枚・長辺1800px・約780KB | **1人10枚まで**。長辺1400px・約400KB以下に縮小(1人 約4MBまで)。自動では消えない(自分で消す) |
| 予定に付ける写真 | 枚数の制限は広い・長辺1280px・約500KB | **1つの予定に3枚まで**。長辺1280px・約150〜200KB以下に縮小(位置情報は消す) |
| 予定の写真の保存期間 | 予定の日から3か月 | **予定の終了日から1か月**で消す(決定)。予定の前に付けた写真が、予定の日より前に消えないようにするため。毎日3時の自動削除で Storage から消す。予定の題名・日付・メモは残る |
| 繰り返しの予定(誕生日など) | 写真は消えない | 消える対象から外す(毎年続くので)。ただし枚数の制限は同じ |
| カレンダー(予定・スタンプ)の見返し | 制限なし | **過去1年まで**。それより前は毎日3時に自動で消す(繰り返しの予定の元の1件は、終わるまで残す)。画面も、今日の1年前までしかさかのぼらない |
| 勤務の記録 | 前月の1日より前を削除 | 上の「保存期間は前後1年」と同じ(13か月前より前を削除)。カレンダーの1年と合わせる |

- 容量の目安: 画像の置き場 1人 約4MB(10枚)。予定の写真は1か月分だけなので、1人あたり多くて数MB。1,000人でも数GB に届くのは「全員が10枚を使い切り、毎日写真を付ける」場合で、Storage の無料枠(1GB)を超える。**人数が増えたら、管理画面で使用量を見て、画像の枚数かサイズを下げる**(作るときに使用量の表示を入れる)

- 名前は「shiftflowカレンダー」(短い名前は「カレンダー」)。アイコンは、ご提示の写真(`docs/mycalendar/icon-source.jpg`・「B 快速」の行先表示)を正方形に切り出して、192px・512px・マスカブル(余白あり)・apple-touch-icon(180px)を作る。文字が小さいので、「B 快速」の表示部分を大きく切り出す。作るときに、できあがりを見てもらう

## 6. 気づいたこと
1. **家族の共有が消える**: 移植元は家族全員が同じ1つのカレンダーを見る作り。ここは1アカウント1人なので、家族でスタンプや TODO を共有する使い方はできなくなる。共有はURLを教えてログインしてもらうか、Google の同期に任せる(決定済み。設定の説明に書く)
3. **予定を Google に同期するか**: 勤務は Google に登録できる。カレンダーで自分で作った予定(歯医者など)も Google に出すかは、まだ決まっていない。出すなら、予定の追加にも「Google にも登録する」のチェックと、直したとき・消したときの同期が要る(大きめの追加になる)。まず勤務だけで始めるのがおすすめ
4. **容量**: 上の3章のとおり、無料枠を超えるのは写真が多いとき。枚数とサイズを小さくしても、使用量の表示は先に入れたい
5. **Safari と追加したアプリでログインが別**: iPhone は追加したアプリで最初に1回ログインが必要(上の4章)
6. **範囲の重なり**: 勤務登録と カレンダーの manifest の範囲が重なる問題(上の4章)。フォルダを分けて避ける
7. **移植元の確認が済んでいないところ**: 画面の1,700行のうち、スタンプのドラッグ・2か月表示・月の画像の書き出しは、スマホと PC の実機でないと動きが確かめられない。移植後に、実機で確認する項目に入れる
8. **作りの大きさ**: 画面だけで移植元は約1,700行。給与・Google 取り込み・バックアップを外しても約1,100行の移植になる。1回で全部ではなく、5章の順に分けて反映する
9. **祝日**: 移植元は Google の公開カレンダーから取る。shiftflow はすでに祝日を持っているので、それを使う(移植元の `ical.js` は持ち込まない)
10. **ラベルの初期値**: 新しく使い始める人に、ラベル(例: 勤務・休日・自分・家族・その他)を最初から用意するか。移植元の `seed.sql` は、家族向けの名前なので使わない
