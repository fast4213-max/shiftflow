N1〜N4 の案
- N1(見送り。#1 を直すときに一緒に直す): 照合の前に、DB の1回の呼び出しで「ロック中なら拒否、そうでなければ回数 +1」。成功したら消す。混雑(429)は数えない仕様を保つ
- N2(済): `calendarAccessError` で、回数制限の理由(rateLimitExceeded・userRateLimitExceeded・quotaExceeded)は 403 でも 502「混んでいます」にする。接続テストは混雑・障害では検証済みを外さない。テスト2件
- N3(済。code が無い古い Auth の 400「Invalid login credentials」だけは、全員が止まらないよう従来どおり「違う」): `error.code === "invalid_credentials"` のときだけ「違う」。他は「ただいまログインできません」(数えない)。テスト1件
- N4(見送り。実害は、ログイン済みの人が容量を埋める場合に限る。やるなら最小版は 画面の `maxlength` と `shift_records` の `check` だけ): 画面に `maxlength`(番号30・メモ200など)、`register-month` で長さを検査、`shift_records` に `check`(先に既存データの長さを確認)、`jsonb_typeof(p_entries) = 'object'` の検査

補足(任意)
- 使い方の「PINは管理者にも分からない」に、「管理者はPIN再設定でその人として入れる(本人はログアウトされる)」を足すと正確
- ログイン切れ後も、画面から DB を直接読み書きする経路は、トークンの期限(既定1時間)まで通る。Supabase の「JWT expiry」を短くすると縮められる(設定のみ)。見送り(小規模な職場内の利用のため。2026-10-06)
- README の「Rate Limits(サインインの回数)」は、ソース上は「トークン更新」と同じ枠(既定: 同じ接続元から5分に150回)。ダッシュボードの表記は未確認
